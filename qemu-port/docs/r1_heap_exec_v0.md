## 3. Vectors and interrupts — the 0x20/0x21 conflict is closed (static)

The earlier worry (`genuine_glue.cpp` `QemuInstallIrq0` and `KbdTakeover` comments naming IDT[0x20]/[0x21]) applies only to
the older Phase-9 "genuine" link set (`GEN_LINK_OBJS`: `irq_gas.o`, `genuine_glue.o`, `genuine_console.o`). It **does not
apply to `kernfull.elf`** [S Makefile:267 vs :50; A `nm`: no `Irq0Stub`, `Irq1Stub`, `QemuInstallIrq0` in kernfull].

For `kernfull` [A/S]:

- `QemuVariantAsic::Init1` masks the PIC, `RemapPic(0x30, 0x38)`, programs the PIT, calls `QemuIrqBindTickKbd`, then
  `X86::SetIrqHandler(&X86IrqDispatcher)`. IRQs 0/1 stay masked until `Init3`.
- `QemuIrqBindTickKbd` also calls `SetupExecGates` (bootstrap IDT in `.bss`, DPL3 gates 0x20/0x21 → `__X86Vector20/21`
  0x118e30/0x118ed0 — type 0xee, i.e. 32-bit **interrupt** gates).
- `A::Init1` (0x1199f0) calls the genuine `X86::Init1Interrupts` (0x117a40) at 0x119a65. That function builds the IDT in
  the CPU page with DPL3 **trap** gates at 0x03, 0x20, 0x21 and interrupt gates at ≥0x30, from `TheExcVectors`
  (decoded from ELF data: 0x20→`__X86Vector20` 0x118e30, 0x21→`__X86Vector21` 0x118ed0, 0x30→`__X86Vector30`) and `__lidt`.
- Hardware IRQs are therefore at 0x30-0x3f and cannot collide with 0x20/0x21 **[I]**.

Residual unknowns **[U]**: (a) `variant/e32load.cpp:25-27` says the port "never runs the genuine `X86::Init1Interrupts`"; the
linked `A::Init1` does call it, so that comment is either stale or `A::Init1` is not reached in this boot path — not
resolved statically. (b) `Init1Interrupts` writes the TSS descriptor into the CPU-page GDT but the live GDT is `qemu_gdt`
(`bootcpu_gas.S`); `TssInitOnce()` sets `X86_TSS_Ptr = qemu_tss` and `ESP0`, which is consistent with that split. Whether the
first ring-3 reschedule uses the live TSS is a runtime question (vector HE-1).

## 5. Genuine hybrid heap on that chunk — traced end to end

Starting point: `t_cactw.exe` header heap min/max = 0x1000 / 0x100000, stack 0x2000 [A]; `fhserver.exe` the same. The port
passes these through `pinfo.iHeapSizeMin/Max` (`e32load.cpp:667-668`) [S]. `euser.dll` links the hybrid heap
(84 `RHybridHeap::` symbols; `RHybridHeap::Alloc` @0x100365a0) and `USE_HYBRID_HEAP` is 1 outside `__WINS__`
(`heap_hybrid.h:24-28`) [S/A].

### 5.1 Walk for `t_cactw` main thread (page size 0x1000)

1. `RunThread` → `SetupThreadHeap` creates the heap when `iAllocator` is null and `iHeapInitialSize > 0` (`up_utl.cpp:137`) [S].
2. `UserHeap::CreateThreadHeap` (`heap_hybrid.cpp:3254`): `minLength=0x1000`, `maxLength=0x100000`; chunk `$HEAP`
   created with `SetThreadHeap(0,0x100000)` then **`SetDisconnected(0,0,0x200000)`** (max doubled). Page size comes from
   `UserHal::PageSizeInBytes` → `EExecHalFunction` (slow 79) → `K::KernelHal` → `M::PageSizeInBytes` = 0x1000. `K::InitHalEntryArray`
   (sets group 0 `kernelHal`) is called from `K::Init3` at 0x128ed3 [A]. Runtime value of the answer [U].
3. `ChunkHeap(RChunk,…)` (`:3058-3250`): `aMaxLength = 0x200000`, not `dlOnly` (offset 0, max>min) → `offset = maxLength = 0x100000`
   (half the chunk). **`aChunk.Commit(0x100000, 0x1000)`**:
   - Direct model returns `KErrNone` → "disconnected" branch: heap object placed at `Base()+0x100000`, `aMaxLength = 0x100000`.
   - It is **not** `KErrGeneral`, so `useAdjust` stays false and `Adjust` is never used for this chunk.
4. The heap object lives in the already-allocated, already-zeroed upper half (§4), so initial commit/addressability holds [S/I].
5. `RHybridHeap::Construct`: `iMinLength != iMaxLength` → not forced fixed-size; `aDLOnly` false → `Init(SLAB_CONFIG=0xabe, 16)`.
   `iSlabInitThreshold = DELAYED_SLAB_THRESHOLD = 64 KB` (`:34,357`), so the slab config is applied only once `iChunkSize ≥ 64 KB`.
6. DL growth (`SysAlloc` → `Map(p!=NULL, asize)`, `:1431,1834-1846`): `iUseAdjust` false → `chunk.Commit(iOffset + (p - this), sz)` →
   `KErrNone` no-op → `iChunkSize += sz` until `iMaxLength` (heap max ≈ 1 MB for `t_cactw`). Past that, `Map` returns 0 and the alloc fails normally.
7. When `iChunkSize` reaches 64 KB, `SlabConfig` is applied (`iSlabThreshold = 49`). A small allocation then calls
   `SlabAllocate → AllocNewSlab → AllocNewPage → Map(0, 0x1000)` (`:2080`). `Map` with `p == NULL` calls `chunk.Allocate(sz)`,
   which returns -5 (§4) → `Map` returns 0 → `AllocNewPage` returns 0.
8. A sized ≥ 64 KB request (`iPageThreshold = 16`) takes `PagedAllocate` (`:2536`), whose `Map(0,n)` fails the same way.

### 5.2 Fallback — this changes the earlier prediction

`RHybridHeap::Alloc` (`:540-600`) falls back to `DlMalloc` when `SlabAllocate` or `PagedAllocate` returns NULL. Confirmed in
compiled euser [A]: `RHybridHeap::Alloc` @0x100365a0 calls `PagedAllocate` (0x10035bc0) / `SlabAllocate` (0x100364d0), then
`test eax,eax; je 100365ea`, the `DlMalloc` (0x10033b30) path. **Large and small allocations therefore still succeed from the DL zone;
the earlier "large allocations would fail" statement in closure §8 is withdrawn.** `PagedEncode`'s `Map(0,…)` (`:2766`) and
`PagedReallocate`'s `Map(p,…)` are reachable only after a successful paged allocation, which never occurs.
`Unmap`/`SysTrim` for the DL top uses `Decommit`, a no-op success, and `iChunkSize` is decremented consistently [S].

Behavioural consequences, all **[U] until run**:

- Heap capacity is the DL half only (`maxLength`), not `2 × maxLength`.
- Once the heap passes 64 KB, every small allocation makes one failing slow exec (`Allocate`) before the DL fallback
  (no spare page is ever cached). Correctness is unaffected; cost is a performance question.
- Memory reservation: each `$HEAP` chunk reserves and clears `2 × heapmax` (2 MB for `t_cactw`) at creation. Pool size
  against the number of processes/threads: `MM::UserDataSectionBase/End` come from the ROM header and super page
  (`minit.cpp:27-47`); port values `kQemuUserDataAddress = 0x2000000`, RAM 128 MB. The pool size the port ROM synthesis
  publishes was not decoded [U].
- `ConstructLock` creates a local mutex and duplicates handles (`EChunkHeapDuplicate`), which depends on those exec paths working [U].

### 5.3 Option verdicts (H1/H2/H3 as defined in closure §8)

| Option | Verdict from this trace |
|---|---|
| **H2** "force DL-only so only `Adjust` is used" | **Not available as stated.** `iUseAdjust`/`iDLOnly` are not flags a caller can set: `ChunkHeap` derives them from `Commit`'s result. `useAdjust` is true only when `Commit` returns `KErrGeneral`, i.e. the chunk is *not* disconnected. A disconnected chunk's `Adjust` returns `KErrGeneral`, so it could not work either. The `Adjust` path would only be reached by a euser built with `USE_HYBRID_HEAP=0` or a normal-chunk heap, i.e. a **euser rebuild or patch, out of scope here**. If one is ever considered, `Adjust` + `fix_mchunk_adjust.py` already works for normal chunks [S]. |
| **H3** private heap bypassing `SetupThreadHeap` | **Not needed**; it would abandon genuine startup. Rejected. |
| **H1** make disconnected `Allocate` work | **Not required for correctness** (the fallback in §5.2 covers it). Optional fidelity/performance work; needs per-chunk page-allocation state and the "lower half only" rule (`r ≤ iOffset`, `Map` at `:1853`). A kernel change; outside this card. |
| **H0 (new)**: no heap or kernel change; accept the documented DL-only behaviour | Smallest. The *prediction* is: genuine startup creates a working heap. **Selection is for the integrator and owner; runtime vectors HE-3…HE-6 must confirm it.** |

## 6. Startup, relocation, absent marker, entry frame — corrections to closure §6/§13

Confirmed and unchanged **[S/A]**: `_E32Startup` layout (`jmp +16`, zero word at `entry+12`, `ebx<2` → `RunThread`, `ebx==4` →
`HandleException`, other → `Invariant`); `RunThread` order (`SetupThreadHeap`, `DllSetTls(KGlobalDestructorTlsKey…)`,
`User::InitProcess` on the first thread via `StaticCallList`/`StaticCallsDone`, `constructStatics`, `E32Main`, `User::Exit`).
Entry offsets: `t_cactw.exe`/`fhserver.exe` 0x260, `euser.dll`/`efsrv.dll` 0x264. `t_cactw` code bytes at entry:
`eb 0e` then zeros through `entry+15` ✓.

Kernel entry frame (`DThread::EpocThreadFunction` 0x11a6b0, `ckernel.cia`) **[S/A]**: user stack filled with `0x29292929`; create
info copied to the user stack; `iret` frame CS 0x1b, SS/DS/ES/GS 0x23, EFLAGS 0x41202 (IF=1, IOPL=1, AC=1); EIP = `DProcess::iReentryPoint`
(initialised from `iCodeSeg->iEntryPtVeneer`, `sprocess.cpp:505`); `ebx` = 0 for the first thread / 1 otherwise, `ecx = ebx`. Exception
re-entry (`ckernel.cpp:156-170`) sets `eip = iReentryPoint`, `ebx = KModuleEntryReasonException (4)`.
`StaticCallList` clears `KThreadFlagOriginal`, then `WriteCallList` writes each `iEntryPtVeneer` with the process entry last.

### Corrections

| # | Earlier statement | Correction |
|---|---|---|
| C1 | G5: no trap-frame/StaticCallList/reentry implementation | Present in the linked kernel (§2.2). Port must not implement them. |
| C2 | §8: large (paged-size) allocations would fail | They fall back to DL (§5.2). Capacity is half the chunk. |
| C3 | §13 rule 6: reject all relocations but 0x3000 | Already overruled by the coordinator. Keep 0x1000/0x2000/0x3000; the port's `ApplyRelocs` (`e32load.cpp:211-241`) matches `sf_lepoc.cpp:183-187` [S]. |
| C4 | Absent marker "equals the entry offset" (a representation left open) | See below. |
| C5 | `entry+12` stamp placement | The slot is at **run address of entry + 12**: `csid_addr = iFileEntryPoint + 12 − iCodeRunAddress + iCodeLoadAddress` (`sf_lepoc.cpp:2524`); the stamp happens only if the word is 0 and only after `RelocateExports`. |
| C6 | `e32load.cpp` status | Verified by grep: **no** absent-marker comparison and **no** code-seg-ID stamping exist in `e32load.cpp` (only an unrelated comment at ~743). The genuine-mode loader is entirely future work. |

**C4 detail.** The exporter's directory entries are *offsets* in the file; `svRelocateExports` (`sf_lepoc.cpp:390-452`) adds
`iCodeRunAddress` to every entry in `[0, codeSize)`. The absent marker is an entry equal to the image's entry *offset*, so after
relocation it equals the entry's **run address**. `svFixupImportAddresses` compares `exportDir[ordinal]` with
`absentOrdinal = exporter.iFileEntryPoint` (`:528,657`) and uses the entry unmodified as the new IAT value ("already been relocated").
For this to hold, the compared `iFileEntryPoint` must be in run-address form at that point. `E32Image` sets it as an *offset* at
construction (`:1872`, "just an offset at this stage"), and the kernel converts it (`pcodeseg.cpp:293`, `aInfo.iFileEntryPoint += ri.iCodeRunAddr`);
`:1523` and `:2524` use it in run-address form. **The exact statement that converts the loader copy was not located [U];**
the contract must nevertheless say: compare relocated-entry to relocated-marker, in a single representation, and never add
the base twice. The port supplies the *offset* to `Kern::ProcessCreate` (`iFileEntryPoint = iEntryPtVeneer = info.iEntry`, `iCodeLoadAddress = 0`),
which the kernel converts, matching the genuine pattern [S].

## 7. Minimal port-owned bring-up design (proposal, not frozen)

Principle: keep genuine EUSER and the genuine kernel exec/heap behaviour; add loader-side port code only.

| ID | Item | Basis |
|---|---|---|
| D-1 | **Heap: no change (H0).** Document explicitly: slab and paged sub-allocators are unavailable in the direct model; the DL zone is the heap; `Allocate` on disconnected chunks returns `KErrNotSupported`. Add a regression note, not a patch. | §5 |
| D-2 | Pass the E32 header heap min/max/stack to `TProcessCreateInfo` unchanged and require `iHeapSizeMin > 0` for images that run genuine startup, since `SetupThreadHeap` skips heap creation otherwise. | `up_utl.cpp:137` |
| D-3 | **Dependencies:** to execute `StaticCallList` meaningfully, `euser.dll` (and any other DLL) should exist as a `DCodeSeg` with `AddDependency` from the EXE and `iDepCount` set, rather than the current `iDepCount = 0` and a resident-image scheme. This is a kernel-mode call sequence on the existing objects (`NewCodeSeg`, `Create`, `Loaded`, `AddDependency`), not an exec from ring 3 (§2.4). `euser.dll` has no writable data (`data=0, bss=0`), so one shared code copy is sufficient [A].
