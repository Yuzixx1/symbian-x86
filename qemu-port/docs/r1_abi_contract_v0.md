# R1-ABI investigation — contract candidate v0 (NOT FROZEN)

Research snapshot: port HEAD `fa62323eea7bc96cefd666e40f5189567731bd44`, upstream read-only `kernelhwsrv/` HEAD `0c3208650587ac0230aed8a74e9bddb5288023eb`. This report is evidence for an integration decision, **not** proof of binary compatibility or permission to implement a guessed ABI. No upstream files were changed. Paths below are relative to the workspace root.

## Binary/toolchain boundary

- Genuine EUSER is a DLL (`kernelhwsrv/kernel/eka/euser/euser.mmp:23-25`); its build includes `cbase/ub_act.cpp`, `ub_svr.cpp`, descriptors, common memory/heap, x86 `.cia` and C++ companions (`euser.mmh:29-55,100-123`). It is not just the active scheduler or a three-call stub. `ub_act.cpp:28-41,70-99,745-795,814-859,1135-1139` defines construction, cancel/wait, install/add/start/stop behavior. `CActive::Cancel` calls `DoCancel`, waits for completion, then clears active flags: timer/request accounting is part of this ABI.
- **Two incompatible export sets are present:** `kernelhwsrv/kernel/eka/bx86/euseru.def:1-12` starts with `memclr @ 1`, MSVC-style `__thiscall` CActive ctor @ 9; `kernelhwsrv/kernel/eka/bx86gcc/euseru.def:1-18` begins with Itanium-mangled `_Z16PanicTFixedArrayv @ 1` and has distinct constructor/destructor entries. Never combine a GCC-built app's imports with bx86 ordinals. `bx86/euseru.def:1053,1657` puts scheduler Install @ 1052, Start @ 1656 **only for that export set**. Toolchain/ABI selection, calling convention, runtime startup and matching import libraries remain unverified. Existing port uses freestanding GCC `-m32 -march=i486` and ELF→E32 conversion rather than an upstream SDK build (`qemu-port/user/user.mk:1-6,37-48`). The pilot EUSER ordinals 1–3 are explicitly transitional (`qemu-port/docs/full_os_checklist.md:101-105`).
- EFSRV is a **separate DLL**: `kernelhwsrv/userlibandfileserver/fileserver/sfsrv/efsrv.mmp:24`; `fileserver/bx86/efsrvu.def:38,45,70,141,153-160,170,181,205,214-221` lists RFs::Connect @ 37, RFile::Create @ 44, Flush @ 69, Open @ 140, Read overloads @ 152–159, Replace @ 169, Seek @ 180, Size @ 204, Write overloads @ 213–220 in the bx86 export set. These are **not** EUSER imports. No `fileserver/bx86gcc/efsrvu.def` was found in this checkout; a complete GCC x86 EFSRV export/import-library story is a blocker, not something to synthesize silently.

## App-visible RFs/RFile candidate contract (source-level, upstream-backed)

- `RFs::Connect` connects to `!FileServer` with `Version()` and message-slot count (`fileserver/sfsrv/cl_cli.cpp:219-245`); `Version()` constructs major/minor/build (`cl_cli.cpp:318-328`, `fileserver/inc/f32ver.h:35,48,61`: 2.0.4011). Default slots are -1 (`fileserver/inc/f32file.h:100`). Server must create independent sessions and negotiate the version rather than treating the name as a device channel.
- Operations are enumerated in declaration order, starting at zero, in `fileserver/inc/F32plugin.h:42-105`: MkDir 16, Delete 19, Rename 20, file subsession close 27, Open 30, Create 31, Replace 32, Read 34, Write 35, Seek 38, Flush 39, Size 40. **Do not treat these numbers alone as a complete wire spec:** masked IPC function bits and subsession handle placement must be checked against `RSubSessionBase`, `TIpcArgs`, and server dispatch before freeze.
- Client call shapes: `cl_cli.cpp:1489-1522,1595-1649,2070-2165` covers session path, MkDir/MkDirAll, Delete, Rename; `fileserver/sfsrv/cl_file.cpp:473-525,531-546,552-594,602-649` sends name descriptor + mode to `CreateSubSession` for Open/Create/Replace and closes by `EFsFileSubClose`. `cl_file.cpp:697-719,865-896,1099-1115,1216-1241` sends read/write descriptor in slot 0, requested length in slot 1, and current-position sentinel or explicit signed 32-bit position in slot 2. `cl_file.cpp:1429-1469,1479-1495,1526-1539` uses descriptor-marked arguments for seek/size, and explicit Flush. `cl_file.cpp:727-755,1068-1093,1121-1142` exposes asynchronous completion/cancellation: not equivalent to immediately completing every IPC call.
- Ordinary `RFile` offsets and `Size(TInt&)` use signed 32-bit values (`fileserver/inc/f32file.h:2400-2462`, `cl_file.cpp:1429-1469,1526-1539`). Larger-file APIs use **RFile64**, not a silent 64-bit reinterpretation of RFile (`fileserver/inc/f32file64.h:83-160`, `cl_file.cpp:2337-2342,2787`). Test >64 KiB separately from >2 GiB and near-4 GiB. `f32file.h:950-1132` documents share-mode matrix and flags; exclusive/readers-only/any/readers-or-writers and read/write permissions need multi-client negative tests. File error constants are `kernelhwsrv/kernel/eka/include/e32err.h:38-107,154,186,198,220,232,309,362,374,397` (not found -1, already exists -11, path not found -12, in use -14, server terminated -15, access denied -21, EOF -25, disk full -26, bad name -28). Actual per-operation mappings require server-side confirmation.
- Today the port exposes PortFile snapshot/buffer channels with a 64 KiB limit, not RFs (`qemu-port/docs/full_os_checklist.md:133-152`). Do not alter its semantics as a surrogate for the RFs app boundary.

## Proof source selection

**Candidate, not selected:** upstream `kernelhwsrv/userlibandfileserver/fileserver/etshell/` (`eshell.mmp:24-46`, `ts_main.cpp:29`, `ts_com.cpp:2207,3253,3630-3632`) is a real file utility with RFs/RFile and `euser.lib efsrv.lib hal.lib`, but is a large interactive shell and needs console/HAL/other services outside R1. Upstream `kernelhwsrv/kerneltest/f32test/group/t_file.mmp:18-31` builds a test binary with EUSER/EFSRV/HAL and TCB/DISKADMIN/ALLFILES; also unsuitable as an ordinary unprivileged proof without dependency pruning (which would violate unchanged-source proof). `kerneltest/f32test/tools/bigfilewriter.cpp:23-28` is **Windows host code**, despite its `.mmp`; reject as E32 proof. **No independently feasible unchanged, unprivileged upstream file utility with active scheduling was established.** R1-PROOF must select one by inspecting its complete source, MMP/library/capability/console graph and reproduce its unmodified toolchain build *before* claiming this contract frozen.

## Proposed fixture/gate sequence (not executed)

1. Select one consistent x86 ABI and upstream toolchain; record executable source/MMP revision, compiler and import-library hashes. Build unmodified upstream app and EUSER/EFSRV from the matching ABI; inspect E32 imports, ordinal/name mapping, UIDs, relocations, entrypoint, and DLL dependencies. Reject missing/wrong-ordinal imports and damaged images without leaked process/segment objects. If bx86gcc EFSRV import metadata cannot be obtained, stop for an explicit veneer/version decision.
2. On a *disposable* uniquely named FAT image: connect twice to `!FileServer`, create nested path, create/write >65536 patterned bytes across 65535/65536, Flush/Close, reopen/seek/read/verify, assert zero-length EOF and missing-file/path codes, restart QEMU and reverify. Exercise share matrix (writer vs exclusive/readers-only/any), duplicate create, directory rename/delete, per-session paths, server death with outstanding request, restart and close/handle cleanup. Compare observed codes with upstream dispatch before locking expectations.
3. Install scheduler, start one timer and an overlapping async file operation, verify completion priority/order, cancel one pending request and verify exactly one completion, exit cleanly. Run unchanged x86 E32 as a normal user process; archive serial log and image hash/identity. Integrator wires targeted regression plus manual step and combined stable suite; physical-PC result is separate.

## Freeze blockers / handoff

**Not frozen.** Confirm: (a) specific unmodified unprivileged upstream proof source with scheduling and write/read; (b) exact x86 compiler ABI plus matching EUSER/EFSRV import libraries and ordinal stability; (c) full `RSubSessionBase` IPC framing, descriptor ABI and server-side request dispatch; (d) startup/TLS/heap/leaves and loader reloc/import behavior; (e) precise share/error/path/EOF/async semantics against upstream server tests; (f) whether port FAT supports directory mutation, flush and streaming offsets. Proposed ownership: integrator chooses proof/toolchain first; R1-EUSER and R1-FS agree import and transport interfaces; R1-FAT validates backend; only then freeze `R1-ABI/v1` and start implementation. This report alone is not that freeze.
