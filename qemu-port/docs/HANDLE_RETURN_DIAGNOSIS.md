# HANDLE_RETURN_DIAGNOSIS — ord-211 Connect: iHandle==0 (2026-11-24)

Root cause: the exec handle is NOT lost; exec 128 returns KErrNotFound(-1) and iHandle==0 is only the SetReturnedHandle error path (e32cmn.inl:3060, inlined in EUSER.DLL ord 211 @0x100159c2 `mov [edi],0`). Handle return itself is proven intact: int 0x21 saves exec EAX (nkernsmp/x86/vectors.cia:257) and pops it to ring 3 (:280); raw exec4(128,..) returns valid handles (/tmp/opencode/diag_prove.log:1335 SessionCreate=0x52820000, EConnect=0); EWCLIENT, importing the SAME ord 211 (EWCLIENT.E32 IAT 0x40d014), gets Create r=0 (genuine_ewsrv.log:921).
The real defect is the server NAME. Port g++ -m32 emits _L/_LIT literals with 32-bit TText (EWSRV.E32 @0x409a5c, EWCLIENT.E32 @0x400c20: 21 00 00 00 45 00...), but prebuilt EUSER.DLL is true 2-byte TText: TPtrC16(const TText*) ord 1169 (EUSER.DLL 0x1002cac0 -> strlen @0x100104e0 scans 2-byte WORDs) reads that as "!"+NUL, length 1. Hence patched/ws_main.cpp:128 Start(_L("!E32WindowServer")) registers the server as "!" and patched/co_cli.cpp:24 looks up "!" — they match. user/ws_e32_client.c:146-150 / desktop.c:128-141 hand-build a correct 2-byte UTF-16 "!E32WindowServer" (len 16) -> ord 211 name8.Copy (us_ksvr.cpp:2289) -> exec 128 FindByName (sipc.cpp:1383) fails -> r=-1, iHandle=0. Logs: dt4_probe.log:891 "DT: dbg ... r=4294967295 h=0"; chunkb_guihello.log:884 "GLDBG: lit-name connect r=-1 handle=0".
Fix (port-side only, kernelhwsrv/ untouched): build genuine images with 16-bit TText (-fshort-wchar / TText=TUint16) and rebuild EWSRV.E32+EWCLIENT.E32 so both use the real "!E32WindowServer"; ws_e32_client.c then works unchanged. Workaround: hand clients connect to "!".
Discriminating test (one boot, hand client): exec4(128, eptrc8("!"),3,0,0) must return a valid handle with EConnect r=0 while exec4(128, eptrc8("!E32WindowServer"),...) returns -1 — proves handle return is fine and the registered name is "!".
