## Highest-value unchanged candidate: FHServer.exe + its client

**Source/build graph:** `kernelhwsrv/kerneltest/f32test/group/fhserver.mmp:18-34` builds an EXE from `fileshare/handshare.cpp` and `fileshare/handshareint.cpp`; links `euser.lib efsrv.lib`, uses Symbian system includes and `CAPABILITY NONE` (UID2 0, UID3 0x2323). `fileshare/handshare.cpp:18-21,50-102` includes `e32svr.h`, `e32test.h`, and `handshare.h`; defines two `CServer2`/`CSession2` servers. `fileshare/handshareint.cpp:19-29,31-78` supplies the session client and IPC methods. `fileshare/handshare.h` is an additional local header; all source is in this checkout. Source-declared direct link dependencies are EUSER and EFSRV; `RTest` adds console/test-output and assertion dependencies in practice, and both libraries may have further transitive dependencies. Do not infer a two-DLL final import table without a binary.

**Behavior:** `handshare.cpp:595-617` calls RFs private-path/session-sharing methods, replaces/writes/closes/reopens an RFile and transfers its handle. `handshare.cpp:200-215,253-301,531-553` contains additional file create/open/read/write/verification paths. `handshare.cpp:620-658,662-724` installs CActiveScheduler in two threads, starts the two servers, creates/resumes a second thread, and tests exit/request/handle accounting. It is an *unchanged, zero-capability source candidate combining file access and active scheduling*. However, its main server blocks in `CActiveScheduler::Start` until driven by an external client; it invokes `RTest` and requires CServer2, handle passing, `RFs::ShareProtected`, private paths, process/thread handles, and a matching EFSRV client DLL. It is **not** a minimal standalone read/write/EOF/missing-file utility. `fileshare/t_handshare.cpp:790-855` is the intended driver: `RProcess::Create("FHServer.exe")`, then duplicate/transfer/adopt tests and server stop. Its `group/t_handshare.mmp:18-36` links EUSER/EFSRV/**HAL**, plus shared `server/t_main.cpp`, `fileutils/src/f32_test_utils.cpp`, `t_chlffs.cpp`; `server/t_main.cpp:20-34,86-115` pulls in HAL, raw-disk and filesystem helpers. Though `CAPABILITY NONE`, this paired client is much larger than an R1 service slice. Do not silently exclude its sources or substitute a different test driver while claiming an unchanged test.

**Verdict:** candidate for *later* genuine CServer2/EUSER/file-handle interoperability, **not selected as the R1 acceptance executable**. It would enlarge the R1 service/loader scope beyond ordinary RFs/RFile and still does not explicitly assert EOF/missing-file/persistence. If the integrator accepts an external port-written driver, label that mixed-source experiment separately; it does not satisfy the unchanged-app proof on its own.

## Simpler two-binary option and its limitations

`kernelhwsrv/kerneltest/e32test/group/t_cactw.mmp:18-27` builds one-source `active/t_cactw.cpp`, EUSER only, `capability none`. `t_cactw.cpp:63-80,88-150` defines CActive runner callbacks, `User::RequestComplete`, nested active scheduler waits/start/stop. `t_cactw.cpp:168-260` creates threads and asserts both normal and panic/exit behavior; it depends on RTest, full threading, panic/logon semantics, heap and CBase scheduling. It is a focused unchanged active-scheduling **test**, not a file utility or quick timer smoke. `t_ctimer.mmp:18-26` / `active/t_ctimer.cpp:61-135,167-190` directly exercises CTimer callbacks/cancel but requests `capability all`, so it is **not** the ordinary zero-capability proof without changing its build definition.

For a separate file workflow, `kernelhwsrv/kerneltest/f32test/group/t_dcnone.mmp:18-41` requests `CAPABILITY NONE` but pulls five sources, EUSER/EFSRV/HAL and shared `server/t_main.cpp`/fileutils, and `server/t_dcnone.cpp:127-188,509-590,774-784,987-996` focuses on forbidden system/private paths and access-denial cases, not ordinary close/reopen/EOF. `kerneltest/f32test/group/t_findcapnone.mmp:18-29` is a one-source zero-capability RFs app, but `server/t_findcapnone.cpp:25-53,59-124` only checks `TFindFile` permission denial in protected directories, **no RFile write or read**. `kerneltest/e32test/group/t_logtofile.mmp:18-30` is `capability none` and links EUSER/EFSRV; `debug/t_logtofile.cpp:53-77,159-187,200-227,251-298` has CServer2 scheduler plus RFs/RFile write, but *requires the external `d_logtofile.ldd` trace device* and does not read back the file. Do not present any of these as satisfying the combined gate.
