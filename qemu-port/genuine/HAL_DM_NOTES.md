# HAL + Domain Manager: genuine kernelhwsrv sources as E32 on the x86 port

Built 2026-11-23 with `tools/genuine_build.py` (genuine defines/includes,
`elf2e32.py` packing, `e32read.py` validation). `kernelhwsrv/` is untouched
(git-clean); all outputs and glue live under `qemu-port/genuine/` with
`hal_` / `dm_` prefixes.

### HAL details
- The `HalInternal::{InitialValue,Properties,Implementation}` tables are not
  in the tree; they are generated by the genuine `halservices/hal/halcfg.pl`
  from `inc/hal_data.h` + a variant `values.hda`/`config.hcf`. We use the
  template variant's `config.hcf` unchanged and a local
  `genuine/hal/values_qemu.hda` (ECPU=x86, ECPUABI=x86, EMachineUid=0x100000ad
  = EMachineUid_X86PC, EDeviceFamily=quartz) -> `genuine/hal/gen/hal_{values,config}.cpp`.
- `<kernel/hal_int.h>` is forwarded via a shim header
  `genuine/hal/shim/kernel/hal_int.h` (the Symbian build exports it to
  `epoc32/include/kernel/`; we cannot write into kernelhwsrv).
- Export map: `bx86/halu.def` has duplicate names (`?Get` x2, `?Set` x2), so
  `gen_def.py` re-emits it as `hal_ord<N> @ <ord>` aliases mapped to GCC
  Itanium symbols (e.g. `hal_ord1=_ZN3HAL3GetEN7HALData10TAttributeERi`;
  note `N7HALData...` not `NS_...` because HALData is a class).

## Stubs (all in `qemu-port/genuine/`, documented in the files)

The pipeline imports exactly ONE EUSER.DLL ordinal (915 = RDebug::Printf via
the PE2 IAT slot), so everything else the genuine code references is
satisfied locally:

- `genuine/hal/hal_glue.cpp`: `_start`/`app_main` entry + markers;
  `User::Panic` (print+park), `User::Alloc/Free` (64 KiB bump heap),
  `RProperty::Define/Set/Get` (in-image table for KUidSystemCategory/
  KUidHalPropertyKeyBase+i, so HAL::Set/Get on settable attributes round-trip),
  `UserSvr::HalFunction` x2 -> KErrNotSupported, `__cxa_pure_virtual`,
  `operator new/delete`, and the descriptor ctors `TDesC8::TDesC8(int,int)`,
  `TDes8::TDes8(int,int,int)`, `TPtr8::TPtr8(...)`, `TBufBase8::TBufBase8(...)`,
  `TVersion::TVersion()` (one-liners copied from genuine
  `eka/common/des8.cpp` / `euser/us_func.cpp`, which we cannot link whole).
- `genuine/dm/dm_glue.cpp`: server `app_main` + markers, exercises genuine
  `TTransitionConfig::CheckValues()`.
- `genuine/dm/dm_stubs.S`, `dm_cli_stubs.S`, `dm_policy_stubs.S`: generated
  by `gen_stubs.py` from `nm -u` of the objects -- one `xor eax,eax; ret`
  stub per EUSER/EFSRV symbol (97 server / 37 cli / 1 policy). Link-time
  fillers only; not on the smoke path. `User::Panic` gets a print+park body.
- `genuine/dm/dm_dll_glue.cpp`: `_start` for the client DLLs; the
  domainpolicy smoke twin calls genuine `DmPolicy::GetPolicy/GetDomainSpecs`.

## Validation + QEMU evidence

- `tools/e32read.py --quiet` passes for all five images (run inside
  genuine_build.py and again explicitly). hal_halu.E32: DLL flags,
  UID chk 0x55081da8, 6 exports patched at code+0x1c90.
- `python3 genuine/prove_hal_dm.py` -> **RESULT: PASS**
  (log `/tmp/opencode/hal_dm_proof.log`). It stages `HAL_SMOKE.E32` +
  `DM_DOMAINSRV.E32` + genuine `EUSER.DLL` + portfilesrv, boots
  `build/kernfull.elf`, runs both from the serial shell:
  - `e32run: bind slot 32768 ord 915 -> 003e7898` (x2), `Loaded r=0` x2
  - HALU markers: `HAL::Get(ECPU) -> r=0 value=2 (ECPU_X86=2)`,
    `HAL::Get(EMemoryPageSize) -> r=0 value=4096`,
    `HAL::Set/Get(ELanguageIndex) -> r=0 roundtrip=7`,
    `HAL::GetAll -> r=0 entries=121 ptr=...`, `HALU SMOKE: done`
  - DM markers: `TTransitionConfig(spec).CheckValues -> r=0`,
    `(bad) -> r=-260 (KDmErrBadDomainSpec)`, `iState=2`, `DM SMOKE: done`
  - no `Exc `/`PanicKernExec`/`FAULT:` lines.
- The DLL images themselves (hal_halu, dm_domaincli, dm_domainpolicy) cannot
  be *executed* by the port loader: `E32Run` rejects UID1 != 0x1000007a
  ("EXEC must never start a DLL as a process", variant/e32load.cpp). Hence
  the exe-typed hal_smoke twin for the QEMU run; the DLLs are validated
  structurally (e32read + kernel E32Validate export-target check).

## How efsrv/ewsrv link against these

- Client side: compile against the genuine exported headers
  (`halservices/hal/inc/hal.h`, `domainmgr/inc/domainmanager.h`,
  `domainpolicy.h`, `domaindefs.h`) and bind to the export directories of
  `hal_halu.E32` (ords 1-6 = HAL::Get/GetAll/Set x2 + HalInternal::InitialValue)
  and `dm_domaincli.E32` (ords 1-51 per domaincliu.def) /
  `dm_domainpolicy.E32` (ords 1-3). The port loader currently supports one
  DLL import (EUSER), so the parallel efsrv/ewsrv builders should use the
  `pack_multi.py` + generated-thunk pattern (see `genuine/ewsrv/build_ewsrv.py`)
  to import HALU/DOMAINCLI ordinals alongside EUSER, or link the client-side
  calls statically like `genuine/ewsrv/ewsrv_shims.cpp` does today.
- Server side: `dm_domainsrv.E32` is E32Run-loadable as-is (UID1 exe). Full
  bring-up of genuine `E32Main()` needs real EUSER server exports
  (CServer2::Start, CActiveScheduler, RMessagePtr2, RFs from EFSRV) -- the
  dm_stubs.S placeholders mark exactly that boundary.

## Known limits

- `domainpolicy_v2u.def` ords 4-5 (`DmPolicy::GetStateSpec/ReleaseStateSpec`)
  are not implemented by `src/domainpolicy.cpp` (v2 lives in another policy
  module), so only the v1 def is built.
- HAL attributes with an implementation function route through
  `UserSvr::HalFunction`, stubbed to KErrNotSupported until the port kernel
  grows the HAL executive; constant/settable attributes (the majority) work.
- Code must stay below `iat_off` (0x8000); all five images fit.
